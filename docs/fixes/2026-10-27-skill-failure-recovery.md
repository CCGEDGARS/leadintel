# Skill conversion diagnostics and bounded recovery

The user reported a Failed Copywriters Handbook skill after successful extraction of 440/446 pages. That coverage exceeds the existing 80% threshold. The failure occurred after skill creation was accepted, during the background conversion, not during book upload/coverage approval. The old catch clause collapsed provider timeouts, rejected requests, storage failures and unknown exceptions into the same instruction to check the AI connection. It discarded the underlying detail. The screenshot and stored generic message cannot establish which underlying failure occurred; do not claim a specific provider/cause without a new execution diagnostic.

The worker now persists an allowlisted error code and execution phase, accurate saved-section progress and consecutive retry count. Provider authentication, request/model rejection, billing, rate limiting, timeout, unavailable service, incomplete output and private storage failures receive distinct messages. Raw provider/document/storage errors are never persisted or logged. Support logs contain only skill ID, allowlisted code, phase, attempt and whether a retry was scheduled.

Temporary provider failures retry automatically with backoff, at most three consecutive attempts. Completed sections are preserved and skipped; a successfully saved section resets the consecutive failure budget. Terminal failures stop. Explicit Retry creation resets the retry budget and resumes the independent snapshot. No existing legacy Failed skill is automatically restarted or charged by the migration. Deletion/revision/lease guards still discard stale responses.

The Skills tab shows saved progress even after failure, colors Failed as an error, and displays the diagnostic code/phase. Legacy failures explicitly say their original detail was not recorded. Counts are read from saved section records so old mid-batch failures do not under-report saved progress.
