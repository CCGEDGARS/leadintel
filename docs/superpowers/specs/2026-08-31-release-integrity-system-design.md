# CCGROUP Release Integrity System — Design

**Date:** 2026-08-31
**Status:** Approved direction; implementation pending explicit spec approval
**First implementation:** LeadIntel
**Intended scope:** Reusable across future CCGROUP GitHub/Vercel applications

## 1. Problem

A previously fixed LeadIntel issue reappeared because browser restore/autofill could reinsert a full URL into a field that already rendered a protocol prefix, while newer code was not always the code served by production. The deeper operational failure was that a URL, a recent deployment timestamp, or a visually correct page could be treated as proof that the newest intended code was live.

The existing repository already has useful safeguards: a `release.json` build manifest, CI tests, a release-provenance policy, deployment regression tests, and an agent release-verification skill. However, the final decision that a build is "latest", "live", or "proven" is still partly procedural. The system must become fail-closed and machine-verifiable.

## 2. Goal

Create one reusable release-integrity mechanism that makes stale-build and wrong-version claims difficult to produce and easy to detect. A build may be labelled **PROVEN PRODUCTION** only when one deterministic verification run confirms the complete identity chain for the exact intended revision.

Canonical chain:

`Git SHA -> required CI success -> live artifact reports same SHA -> backend health -> required smoke checks -> machine-readable proof`

For platforms where deployment metadata is available, deployment-provider readiness/identity is an additional gate rather than a substitute for live-artifact verification.

## 3. Design principles

1. **Fail closed.** Unknown, pending, stale, mismatched, skipped-required, inaccessible, or partially verified states are not "current".
2. **Exact revision identity.** Commit SHA is the primary identity, not filename, timestamp, browser state, deployment URL, or branch name.
3. **Live artifact is authoritative for what users receive.** `release.json` must be fetched from the exact production URL with cache busting.
4. **One verification engine.** Human operators, AI agents, CI, and future applications use the same terminology and checks.
5. **No silent fallback.** If the newest intended build fails, the last working production can be described as "last known working" but never as "latest/current".
6. **Feature-aware gates.** Core shell, CRM, Discovery, Outreach/Gmail, migrations, and future modules can add mandatory smoke checks.
7. **Evidence is durable.** Every successful or failed verification produces a structured proof record that explains every gate.
8. **Reusable configuration.** App-specific URLs/checks live in config; verification logic remains generic.

## 4. Components

### 4.1 `release-integrity.config.json`

Repository-owned configuration, containing at minimum:

- `application`
- `productionUrl`
- `manifestPath` (default `/release.json`)
- `backendHealthUrl`
- `expectedRef` (normally `main`)
- `requiredChecks`
- `smokeChecks[]`
- optional provider metadata requirements
- verification timeout/retry policy

Future CCGROUP applications copy the config and reusable verifier rather than inventing a new release process.

### 4.2 Generic verifier: `scripts/verify-release-integrity.mjs`

Inputs:

- expected Git SHA
- environment (`preview` or `production`)
- config path
- optional provider metadata supplied by CI/agent tooling

Checks:

1. Expected SHA is valid and explicit.
2. Live manifest fetch succeeds with a nonce/cache-busting query.
3. `manifest.commit === expected SHA`.
4. Expected service/ref metadata match configuration.
5. Backend health returns HTTP 200 and expected service identity where defined.
6. Configured smoke checks pass.
7. Optional deployment-provider identity/readiness is checked when metadata is supplied.
8. Produces a deterministic verdict: `PROVEN`, `BLOCKED`, or `INCOMPLETE`.

Exit codes:

- `0` = proven
- non-zero = cannot be presented as current/proven

### 4.3 Machine-readable proof: `release-proof.json`

Generated by every verification run and retained as a CI artifact. Schema includes:

- application
- environment
- verification timestamp
- expected SHA/ref
- live manifest SHA/ref
- CI context/run identifier
- deployment identity/readiness when available
- backend health status
- each smoke-check result
- overall verdict
- failure reasons

This becomes the single evidence object an AI agent or human can inspect.

### 4.4 GitHub Actions production gate

A dedicated workflow runs on every push to `main` that affects the deployed application or release system.

Flow:

1. Wait/poll for production deployment propagation within a bounded timeout.
2. Run the generic verifier using `GITHUB_SHA` as the expected SHA.
3. Require live `/release.json` to converge to that exact SHA.
4. Run backend health and configured smoke tests.
5. Upload `release-proof.json` even on failure.
6. Fail the workflow if the exact production revision is not proven.

This converts stale production from a conversational discovery into a visible failed release check.

### 4.5 Preview gate

For pull requests / preview deployments, the same verifier is used against the preview URL when available. Preview proof and production proof remain separate states.

Terminology is fixed:

- `LATEST CODE` — newest intended source revision; not necessarily deployed.
- `VERIFIED PREVIEW` — exact preview artifact passed its applicable gates.
- `PROVEN PRODUCTION` — custom-domain production artifact passed all mandatory gates.
- `LAST KNOWN WORKING` — older production known to work; never presented as latest.

### 4.6 AI/agent operating rule

Add/upgrade the repository release-verification skill so every coding agent must:

1. Identify intended SHA.
2. Read the latest applicable release proof or run the release verifier.
3. Refuse the labels `latest`, `current`, `live`, `production ready`, `deployed`, `fixed in production`, or `proven` unless the proof verdict is `PROVEN` for that exact SHA/environment.
4. If proof is unavailable or stale, state the unresolved gate instead of substituting an older link.

This same rule will govern my future LeadIntel responses.

## 5. LeadIntel-specific smoke profile

Initial production checks:

### Core
- `/customer/` returns HTTP 200.
- page identifies the active Commercial Intelligence workspace.
- required application modules referenced by the active shell are retrievable.
- live `website-input-sync.js` contains the canonical protocol-normalization behavior.

### Backend
- configured `/api/health` returns 200 and identifies `leadintel-api`.

### Release identity
- `/release.json?verify=<nonce>` returns exact expected SHA and `main` ref.

### Regression-sensitive UI
- website input implementation keeps one visual protocol prefix and normalizes restored full URLs.
- production entry point routes to `/customer/`, not legacy V1/V2.

### Feature-specific additions
- CRM-changing releases: migration/schema compatibility + authenticated CRM smoke evidence required before a complete CRM-production claim.
- Gmail/outreach-changing releases: applicable auth/delivery integration smoke evidence required before complete-production claim.

## 6. CI relationship

Existing Customer V2 CI remains the pre-deployment code-quality gate. The new production release-integrity workflow is a separate post-deployment identity/health gate.

Neither substitutes for the other:

- CI proves the revision passed repository tests.
- release integrity proves production is actually serving that tested revision and critical integrations are healthy.

## 7. Error handling

### Manifest SHA mismatch
Verdict: `BLOCKED_STALE_DEPLOYMENT`.
No current/latest production link may be issued.

### Deployment not propagated within timeout
Verdict: `INCOMPLETE_DEPLOYMENT_TIMEOUT`.
Do not fall back silently.

### Backend unhealthy
Verdict: `BLOCKED_BACKEND_HEALTH`.
Frontend may be deployed, but integrated production is not proven.

### Smoke failure
Verdict: `BLOCKED_SMOKE_CHECK` with failing check IDs.

### Verification service/tool unavailable
Verdict: `INCOMPLETE_VERIFICATION`.
Unavailability never becomes success.

## 8. Security and secrets

The generic verifier should not require private deployment-provider credentials for the base proof chain. Public custom-domain manifest and health verification are preferred. Provider API checks may be added when authenticated tooling is available, but no tokens are committed to the repository or embedded in artifacts.

`release-proof.json` must contain operational status only, never secrets, tokens, cookies, API keys, or sensitive response bodies.

## 9. Reusability model

The reusable package consists of:

- `release-integrity.config.json`
- `scripts/verify-release-integrity.mjs`
- `.github/workflows/release-integrity.yml`
- `.agents/skills/release-integrity/SKILL.md`
- tests enforcing config, workflow, proof schema, and fail-closed terminology

Future applications change configuration and smoke profiles, not the core algorithm.

## 10. Testing strategy

Implementation follows TDD.

Required regression tests must demonstrate failure before implementation for at least:

1. manifest SHA differs from expected SHA;
2. backend health failure;
3. missing manifest;
4. stale/cached manifest response does not satisfy proof;
5. smoke-check failure;
6. proof cannot return `PROVEN` with a skipped mandatory gate;
7. agent/release policy forbids presenting an old link as current;
8. LeadIntel duplicate-protocol regression remains covered;
9. production entry point cannot regress to legacy workspace;
10. proof schema contains exact SHA and individual gate results.

Then run full existing Customer V2 CI plus release-system tests and JavaScript syntax checks.

## 11. Rollout

Phase 1: implement and prove in LeadIntel without changing the application architecture.

Phase 2: make the verifier/config/workflow the default template for future CCGROUP GitHub/Vercel applications.

No production link is declared proven as part of Phase 1 until the new system itself passes its own production proof.

## 12. Success criteria

The system is complete when:

- a stale production deployment automatically fails release integrity;
- exact SHA mismatch is visible in machine-readable proof;
- every `main` release receives a post-deployment verdict;
- backend and critical smoke checks are part of that verdict;
- old working versions cannot satisfy a newer SHA's proof;
- LeadIntel's current production passes the new verifier;
- the implementation is documented and reusable for future CCGROUP apps;
- AI agents have an explicit fail-closed rule governing what links/status labels they may present.

## 13. Non-goals

- Replacing Vercel deployment infrastructure.
- Building a large release-management dashboard.
- Storing deployment secrets in the repository.
- Treating all feature E2E tests as mandatory for every tiny change; feature-specific gates are selected by configuration/scope.

The design intentionally solves the freshness/provenance failure permanently without introducing unnecessary release-platform complexity.
