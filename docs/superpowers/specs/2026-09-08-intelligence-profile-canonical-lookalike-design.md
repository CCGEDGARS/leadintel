# LeadIntel Canonical Intelligence Profile + Lookalike Discovery Design

Date: 2026-09-08
Status: Design approved in conversation; implementation pending user review of this written spec

## 1. Purpose

Replace the current partially overlapping intelligence layers with one canonical Company Intelligence Profile that all downstream LeadIntel modules consume. The redesign must also simplify the visible Intelligence Profile and introduce an optional Reference Customer / Lookalike Discovery flow where an activated customer list becomes a high-priority discovery model inside the Step 1 target market(s).

The core problem this solves is inconsistency: profile fields, evidence, inferred pains, gaps, signals, and downstream strategy can currently be generated by different layers at different times. That allows contradictions such as a customer pain being displayed while the gap panel still says the customer problem is unknown, or stale third-party evidence appearing as if it were company evidence.

## 2. Core Design Principles

1. One canonical intelligence state. Every downstream module reads from the same authoritative profile.
2. First-party evidence is primary. External research can validate or challenge, but never silently overwrite first-party truth.
3. Provenance is explicit. Important profile values expose where they came from and their confidence/status.
4. User confirmation outranks inference. A user edit of an inferred value promotes it to user-confirmed truth.
5. Gaps are based on the canonical state, not on whether a specific onboarding textarea was completed.
6. Contradictions are preserved and surfaced, not silently reconciled.
7. The visible Intelligence Profile is concise: facts, interpretation, diagnostics, and evidence are separated.
8. Activated reference customers are treated as a priority discovery model, but hard user exclusions still win.
9. Step 1 target markets remain the single geography source for discovery. Lookalike Discovery must not introduce a duplicate country selector.

## 3. Source Authority Hierarchy

### 3.1 First-party / authoritative sources

Priority order inside the first-party layer:

1. User-confirmed input
2. Uploaded company documents
3. Company-owned website and same-domain pages
4. AI inference derived strictly from first-party evidence

When two first-party sources conflict, the higher-priority source is retained as the canonical value and the conflict is recorded for review.

### 3.2 Secondary / external sources

Examples:
- LinkedIn
- distributor or partner pages
- press articles
- directories
- external case studies
- market research websites
- analyst/reference content

External evidence may:
- validate a canonical claim,
- challenge a canonical claim,
- add market context,
- raise a contradiction.

External evidence must never silently replace a canonical first-party claim.

### 3.3 Company-owned links vs manually supplied third-party links

A manually supplied link is not automatically primary evidence.
- Company-owned / same-domain / clearly company-controlled links: primary.
- Third-party links: secondary, even if the user supplied them manually.

## 4. Canonical Intelligence Model

The implementation should converge current profile-engine, company-brain, business-identity, evidence, gap, and downstream consumers around one canonical object.

The canonical profile must contain at minimum:

### 4.1 Core commercial fields
- company identity / company name
- priority offer
- ideal customer / ICP
- target market(s)
- customer problems / pains
- buying triggers
- decision makers
- differentiation
- commercial objective
- exclusions
- commercial value / opportunity value

### 4.2 Supporting fields
- company overview
- current markets
- reference customer summary
- buying outcomes
- additional commercial context

### 4.3 Per-field metadata
For each important field, store metadata such as:
- value
- provenance class
- provenance source id(s)
- status
- confidence
- last updated timestamp or profile version marker

Recommended statuses:
- `user_confirmed`
- `first_party_evidence`
- `ai_inferred_first_party`
- `external_validated`
- `needs_confirmation`
- `unknown`

Recommended confidence levels:
- high
- medium
- low

A user edit/save of an AI-inferred value changes the field status to `user_confirmed`.

## 5. Canonical Reconciliation Flow

All profile generation must follow one ordered pipeline:

1. Ingest source inputs.
2. Classify every source as first-party or secondary.
3. Extract normalized claims from first-party data.
4. Resolve first-party conflicts using the agreed priority hierarchy.
5. Derive AI hypotheses only from the reconciled first-party state.
6. Build the canonical profile.
7. Compute diagnostics (known / needs confirmation / missing) from the canonical profile.
8. Compare external evidence against the canonical profile.
9. Record contradictions and validations without overwriting canonical values.
10. Expose the canonical profile to downstream modules.

No later module may independently mutate the meaning of a canonical profile field without going through the canonical reconciliation layer.

## 6. Gap Logic

The current model of treating unanswered onboarding fields as gaps must be removed.

A gap means the canonical profile lacks enough reliable information to support a commercial decision.

Three user-facing diagnostic states:

### Known
Enough reliable information exists.

### Needs confirmation
LeadIntel has a reasonable first-party inference, but the user has not confirmed it.

### Missing
There is genuinely insufficient information to form a useful hypothesis.

Example:
- Customer pains inferred from the company website: `Needs confirmation`, not `Missing`.
- User later edits/accepts the pains: `Known / user confirmed`.

The same canonical field state must drive both the visible field and the diagnostic. The system must not show a value and simultaneously claim that the same value is missing.

## 7. Contradiction Handling

Contradictions are a separate diagnostic category from gaps.

Example:
- Primary claim: “Enterprise customers are the primary segment.”
- External source: “SME-focused provider.”

System result:
- canonical value: retain primary claim
- contradiction: record external conflict
- user-facing status: `Primary retained · review recommended`

A contradiction record should include:
- canonical claim
- canonical source(s)
- conflicting claim
- external source(s)
- confidence
- resolution status
- recommended review action

Contradictions should remain hidden when none exist.

## 8. Simplified Intelligence Profile UI

The visible profile should stop behaving like a large database form.

### 8.1 Executive Intelligence Summary
Show 8 concise primary cards:
1. Priority Offer
2. Ideal Customer / ICP
3. Target Market
4. Customer Problems
5. Buying Triggers
6. Decision Makers
7. Differentiation
8. Commercial Objective

Each card shows:
- concise value
- provenance/status
- confidence where relevant

Examples:
- `User confirmed`
- `First-party evidence`
- `AI inferred from first-party evidence · Medium confidence`

AI-inferred cards remain directly editable. Saving an edit promotes the value to user-confirmed status.

### 8.2 Remove from primary view
Move to Supporting Context or derive internally:
- Company Overview
- Current Market Footprint
- Lookalike / Reference Customers list
- Opportunity Value
- Negative ICP / Exclusions
- detailed buying outcomes

Remove `Market Focus` as a separate primary field because it duplicates Target Market + ICP.

### 8.3 Remove duplicated commercial frameworks from the main profile
Do not present these as separate primary profile fields:
- Golden Circle Why / How / What
- FAB Features / Advantages / Benefits
- duplicated value proposition / positioning formulations

They can remain available to Ask LeadIntel or downstream content generation when useful.

### 8.4 LeadIntel Interpretation section
Show only conclusions, not another copy of the facts. Recommended outputs:
- Commercial Focus
- Strongest Opportunity Conditions
- Main Commercial Risk
- Recommended Next Move

### 8.5 Supporting Context
Collapsed by default. Include secondary details such as:
- company overview
- current markets
- reference customer summary
- exclusions
- commercial value
- uploaded documents / additional context
- detailed outcomes

### 8.6 Evidence & Validation
Replace large generic source cards with a compact summary and claim-specific provenance.

Bottom-level evidence summary example:
- First-party website pages: 6
- Uploaded documents: 2
- User-confirmed inputs: 7
- External validation sources: 4
- Contradictions: 1

Provide controls such as:
- View first-party evidence
- View external validation

Third-party market/reference sources must never be rendered as company-level evidence.

### 8.7 Signals
Remove the full Recommended Signal Library from the Intelligence Profile because Step 4 already contains Signal Designer.

The profile may show a compact signal summary, for example:
- `5 active signal themes`
- `Open Signal Designer →`

### 8.8 Review state
Replace generic approval wording with a profile quality summary, for example:
- `7 confirmed · 3 inferred · 1 needs review`

Actions:
- Confirm current profile
- Improve with Ask LeadIntel

New evidence may later create a warning even after confirmation.

## 9. Stale Evidence Cleanup

When the canonical profile is rebuilt:
- active company evidence must be regenerated from the current first-party source set,
- evidence that no longer belongs to the current company/domain must not remain visible as active company evidence,
- stale external evidence may be retained historically if useful, but only under external/reference history, never current company evidence.

This specifically prevents old unrelated sources from surviving as current profile evidence after website/profile changes.

## 10. Reference Customers / Lookalike Discovery

### 10.1 Purpose
Allow the user to upload an existing customer list, activate it, and let LeadIntel learn what successful existing customers have in common. Once activated, this becomes a high-priority discovery model inside the already selected Step 1 target market(s).

### 10.2 Input methods
Supported inputs:
- CSV (recommended)
- XLSX / Excel (recommended)
- PDF (supported, review required)
- manual entry (fallback)

PDF extraction must be treated as probabilistic because tables and company names may be ambiguous. The user must review extracted rows before activation.

### 10.3 Import fields
Where available, parse:
- company name
- website
- country
- notes
- product/service bought
- approximate value
- reason this is a good reference customer

Only company name is mandatory for import. Website is strongly preferred for reliable enrichment.

### 10.4 Review + activation flow
The flow is:

1. Import customer list.
2. Normalize rows and attempt company/domain resolution.
3. Present a review table.
4. User activates the list / selected rows.
5. Only activated reference customers influence the lookalike model.
6. LeadIntel analyzes activated reference companies.
7. LeadIntel creates a Reference Customer DNA profile.

Activation must be explicit. Imported data must not influence discovery before the user activates it.

### 10.5 Activated list becomes priority
Once activated, Reference Customer DNA is a priority discovery input.

Priority hierarchy for discovery:

1. Hard user rules / exclusions
2. Activated Reference Customer DNA
3. Step 1 target market(s)
4. User-confirmed ICP / commercial strategy
5. Buying signals / timing
6. AI-inferred traits
7. External market intelligence

The reference model is powerful but may not override explicit exclusions or hard geographic/compliance rules.

### 10.6 Target geography
Do not add another country selector inside Lookalike Discovery.

The Step 1 target market selector remains the single source of geography.

If Step 1 = Germany:
- Lookalike Discovery means “Find companies in Germany similar to my activated reference customers.”

If Step 1 contains Germany + Poland + Sweden:
- process each market country-by-country internally,
- normalize scoring by market,
- present one combined ranked result view with market labels and filters.

### 10.7 Reference Customer DNA
LeadIntel should infer common commercial traits from activated reference companies, for example:
- industries
- company size bands
- countries / regional characteristics
- business model
- growth stage
- operating complexity
- number of sites / geographic footprint where knowable
- likely buyer roles
- common products/services purchased
- recurring customer problems
- common buying-trigger patterns
- technology / operating stack where relevant and reliably evidenced

Do not infer unsupported traits as facts. Each DNA dimension should retain evidence/confidence.

#### Cross-company support and confidence

Company-level extraction confidence and customer-profile confidence are separate measures. The profile confidence must account for agreement across the analyzed reference companies; several individually high-confidence company analyses do not by themselves support a high-confidence shared profile.

For a list with two or more analyzed companies, a trait enters Reference Customer DNA only when it appears in at least `max(2, ceil(60% of the analyzed companies))` members of the selected segment. Keep one-off observations visible in the review screen with their exact `x/n` support count, but exclude them from Discovery queries and lookalike ranking. A one-company list may be activated as a low-confidence hypothesis.

The profile is high confidence only when at least two dimensions have strong repeated support (at least 80% of the segment) and the underlying company analyses are high confidence. If no trait repeats, show that no shared profile was found and block activation until the list is corrected or expanded. Suggested profiles require explicit user selection; they are not preselected for activation.

Previously published profiles must be recalibrated from current company analyses or recorded per-dimension support before they continue influencing Discovery. Retire a published profile from Discovery when no dimensions meet the support threshold.

### 10.8 Lookalike scoring
Discovery results should expose a Lookalike Match score, for example:
- `Lookalike Match: 92/100`

The explanation should identify why the company is similar, e.g.:
- same company-size band
- similar industry structure
- multi-site operations
- matching growth pattern
- matching buyer roles
- active trigger similar to reference customers

The score should not be an opaque similarity number. It must be decomposable into understandable dimensions.

### 10.9 Relationship to canonical ICP
Reference Customer DNA does not rewrite the canonical ICP automatically.

It influences discovery as a high-priority empirical model. Where it conflicts with user-confirmed strategy, the conflict should be surfaced rather than silently changing the ICP.

## 11. Downstream Consumers

The following modules must consume the canonical profile rather than independently reconstructing company meaning:
- Market Strategy
- ICP Engine
- Signal Designer
- Market Research
- Discovery
- Opportunity scoring
- Outreach / messaging
- Ask LeadIntel Copilot

Lookalike Discovery adds Reference Customer DNA as an additional discovery/ranking input when active.

## 12. Error Handling and Safety Rules

- If no website content is readable, do not fabricate company evidence.
- If a PDF customer list cannot be parsed reliably, mark rows `Needs review`.
- If an imported company cannot be confidently resolved to a website/domain, do not silently guess; mark it unresolved.
- If a reference list is activated but too few companies are analyzable, show limited-confidence DNA rather than a strong lookalike model.
- If target markets change, preserve the activated reference list but recalculate discovery for the new market(s).
- If the company website changes, invalidate/rebuild first-party company evidence and canonical claims; do not retain stale company evidence as current.
- External evidence can never silently overwrite first-party canonical values.

## 13. Testing Requirements

Implementation must include automated tests for at least:

### Canonical source precedence
- user-confirmed input outranks uploaded doc
- uploaded doc outranks website
- website outranks AI inference
- external source cannot overwrite canonical first-party value

### Gap reconciliation
- inferred pain exists -> gap is `needs_confirmation`, not `missing`
- user-confirmed pain -> gap removed / known
- no evidence and no input -> missing

### Stale evidence
- changing company website removes old-domain evidence from active profile
- unrelated external sources never appear in first-party evidence cards

### Contradictions
- external contradiction is retained and surfaced
- canonical first-party claim remains unchanged

### Profile editing
- editing an AI-inferred field changes provenance to user-confirmed

### Reference customer import
- CSV/XLSX parsing and normalization
- PDF extraction review state
- duplicate company handling
- unresolved domain handling
- activation gating

### Lookalike priority
- inactive list does not affect discovery
- active list affects ranking
- hard exclusions still outrank lookalike similarity
- Step 1 geography constrains search
- multiple Step 1 countries are processed per-country and combined correctly

### Regression
- Market Strategy, Signals, Discovery, and Copilot still receive required canonical fields
- current customer CI and backend CI remain green

## 14. Migration Strategy

Do not attempt to preserve stale derived profile/evidence fields as authoritative during migration.

Recommended migration behavior:
1. Load existing saved state.
2. Preserve raw user answers, uploaded document text, Step 1 website/markets, and user-entered source URLs.
3. Reclassify sources.
4. Rebuild the canonical profile from current first-party inputs.
5. Recompute gaps, provenance, confidence, contradictions, signals summary, and downstream strategy seeds.
6. Retain old derived profile fields only as non-authoritative migration history if needed for debugging, not visible current truth.

## 15. Success Criteria

The redesign is successful when:

1. The Intelligence Profile cannot show a field as populated while the diagnostic says the same information is missing.
2. Unrelated third-party sources never appear as company evidence.
3. Every important profile field has traceable provenance and status.
4. User-confirmed data consistently outranks all inference.
5. External contradictions are visible without overwriting first-party claims.
6. The visible Intelligence Profile is materially simpler than the current page.
7. Step 4 signal functionality is not duplicated in Step 3.
8. An activated reference customer list measurably influences discovery ranking.
9. Lookalike searches automatically use the Step 1 target market(s), with no duplicate geography selector.
10. Hard exclusions always override lookalike similarity.
11. Downstream modules use the same canonical profile semantics.

## 16. Out of Scope for This Implementation

- Multiple independently weighted reference-customer lists (e.g. “German customers”, “high-value customers”) in V1.
- A full graph database / knowledge graph migration.
- Automatic CRM ingestion of reference customers.
- Automatic outreach to reference customers themselves.
- Replacing the existing market research modes.
- Rebuilding the whole LeadIntel application outside the profile/evidence/lookalike integration needed for this design.

These can be considered later after the canonical profile and single activated reference-customer model are stable.
