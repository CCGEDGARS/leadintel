# Writing References — implementation and release record

## Behaviour

Message settings contains three workspace-private source cards. PDF, UTF-8 TXT and Markdown are supported up to 20 MiB, 600 PDF pages and 2 million extracted characters. Originals are retained unchanged. Uploads default to inactive. Sources affect only AI Original/Generated email and LinkedIn drafts, including Improve in those modes. Protected styles and numbered personal templates are unaffected. No active sources preserves the ordinary generation request.

Extraction recomputes text and coverage on the server using pinned unpdf 1.8.1's serverless PDF.js build. Every readable chunk is analysed using the workspace's connected active AI provider, with no managed-key fallback. Completed chunks survive provider failures; Retry analysis resumes them. Jobs have bounded leases and provider timeouts; minute recovery runs only reference jobs, while existing hourly monitoring/outreach remains hourly. Mixed readable/unreadable PDFs show Needs attention and cannot activate. No OCR is promised.

Learned techniques have page/line attribution. Generation selects bounded relevant techniques and short private source excerpts; verified business evidence outranks source guidance. Opposing formal/casual tone techniques are conservatively omitted; arbitrary semantic contradictions still rely on the generation instruction to favour compatible guidance and the user's explicit instruction. Sources do not establish customer facts or numerical results. Response provenance contains IDs only, and is saved with the draft. Changing references during a provider request discards the old response.

## Storage and billing boundary

The user activated private R2 and bound `WRITING_REFERENCES_BUCKET` to `leadintel-writing-reference` in the production leadintel-api dashboard. Repository configuration preserves that observed binding. Initial eligibility is explicitly limited to the owner's existing workspace `edgars-latvia`, observed in the authenticated workspace selector. Other workspaces are denied before storage access; the owner's bucket is not a general fallback. User-owned storage/CRM connectors and the broader billing separation task are deferred by user instruction and are not implemented.

Dedicated D1 tables contain slots, source metadata, bounded catalogue previews, per-chunk analysis and durable jobs; R2 contains originals, extracted sections and the full catalogue. The settings UI shows the first 20 techniques with uses, cautions, adapted patterns, locations and the total count; generation selects from the full private catalogue. No source payload enters workspace sync JSON. Session and membership checks apply to each route, with owner-only mutations. Credentials use the existing encrypted workspace AI integration. There are no public source URLs.

Large uploads bypass the first-party function body limit using a two-minute, single-use upload authorization. The authorization is issued through the authenticated same-origin API, stored only as a hash, and sent in the multipart body directly to the fixed Worker endpoint without cookies. Membership and pilot eligibility are rechecked before storage. Tokens are never placed in URLs. Persistent slot revisions and source IDs reject stale replacements, including empty-slot upload/delete cycles. A durable cleanup journal is written before private objects, so interrupted uploads and catalogue writes remain recoverable.

## Deactivation, deletion and retention

Deactivation keeps the document but excludes it from future generation. Delete invalidates influence immediately, clears guidance/instructions and cancels processing, then removes original/text objects, chunks and jobs. Failed cleanup remains visible as Deleting and scheduled recovery retries it. Replacement installs a new inactive source and retires the previous version. Deletion tombstones retain opaque ownership/slot/revision identifiers to prevent late resurrection; document metadata and content are removed. Existing drafts/templates retain their text and historical IDs. Provider retention and storage-provider backup retention are governed by those providers; deletion here does not promise erasure from their backups. Document contents are excluded from application error logs.
