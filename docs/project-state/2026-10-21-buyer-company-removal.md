# Buyers: Refresh, Save, Remove

User confirmed the revised semantics on 21 October 2026. These replace the original save-before-deselect implementation.

- **Refresh** updates buyer identities and contact research through the existing research flow.
- **Save** explicitly saves company/buyer research to CRM. **Saved ✓** is shown after successful save and workspace sync; changed research makes Save available again. Verified contact records retain their separate verification path.
- **Remove** permanently deletes the company, buyers, research, message packages and activity history from this workspace and CRM. It never saves or creates a CRM record first. The existing owner-only deletion API remains authoritative. A styled, cancel-first confirmation names the company and states that deletion cannot be undone.

The user subsequently approved a third option in the Remove dialog: **Cancel | Save to CRM | Remove completely**. **Save to CRM** persists the current company/buyer research, then deselects the company from the Buyers list. It keeps CRM company/contact/intelligence/activity records, saved messages, delivery history, Companies research and seller targets intact. The main **Save** button still keeps the company visible. No archive/suppression or pipeline-stage change is applied.

The dialog's alternative action returns an explicit distinct result; only `true` can enter permanent deletion. Save failure, account/workspace changes or new research during save leave the selection intact. A list-sync failure restores the selection and focus while preserving unrelated concurrent edits and the successful CRM save. The alternative uses the same research/enrichment and duplicate-action guards as removal. Existing two-button confirmations retain boolean results, cancel-first focus, Escape and account-change cancellation. Narrow screens stack the three choices.

Dismissal snapshots contain only Buyers selections and focus. They remain separate from mutable working state so edits made during a pending sync cannot contaminate the rollback baseline. Message and delivery stores are not copied or rewritten by this path. A regression test exercises concurrent selection/message edits during failed sync.

Removal clears the exact company domain from selections, candidate lists, pipeline, known targets, saved buyer drafts, recipient handoffs and delivery activity. Seller configuration, reusable message templates, other companies and other workspaces remain intact. Working-record cleanup is synced before irreversible CRM deletion. On sync/deletion failure the working records are restored without overwriting unrelated concurrent edits. Account changes, active research and duplicate actions are guarded. In-flight CRM reads are invalidated so stale responses cannot reintroduce the company. Mounted CRM, Messages and Delivery views update after cleanup. Pipeline’s separate Remove from Pipeline action continues to preserve history.

Tests: buyer-company-remove.test.js covers real delegated button clicks, the shared three-choice dialog, actual CRM research mapping, saved-history preservation, selection reload, Save state, confirmation/cancellation, owner restrictions, no implicit CRM save on permanent removal, complete cleanup, failure restoration and scope changes. confirmation-dialog.test.js checks the distinct alternative result and keyboard/account guards. buyer-company-records.test.js covers exact-domain cleanup, normalized reload and saved-signature invalidation. The backend CRM test verifies actual SQLite cascade deletion and cross-workspace isolation. Production smoke checks require both removal paths, dialog choice code, cleanup helpers and cache versions. No backend API/schema change is required.
