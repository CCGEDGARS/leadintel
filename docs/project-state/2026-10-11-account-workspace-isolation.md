# Account and workspace cache isolation

Two Google accounts have separate backend users and workspace memberships, but the browser previously kept one unscoped active cache. Sign-out removed only the login cookie. A second account with an empty cloud state could inherit the first account's saved profile through the persistence snapshot fallback. Research, activation, reset intentions, recovery copies and task state also survived.

The early account-cache boundary now parks all LeadIntel workspace storage under the previous workspace ID before detaching it. Unknown guest or legacy data is preserved separately and never adopted by an authenticated account. Cache restoration requires the session user and a workspace returned by the authenticated membership endpoint; login URL parameters only trigger detachment and cannot restore or authorize data.

Sign-out and provider switching verify preservation before logging out, check the logout response, and clear active browser state only after success. Failed preservation or logout keeps the active data. Workspace selection uses the same boundary. Restored caches retain unsynced changes, acknowledged snapshots and recovery copies; normal safe sync reconciliation then runs for the correct workspace.

A shared account-context generation invalidates other tabs. Storage guards reject stale reads/writes immediately, API guards reject workspace mismatches and block background workspace work until session/membership verification, and responses begun before a switch are rejected before persistence can acknowledge or hydrate them. Old tabs refresh to the browser's current login. Regular tabs share one login; simultaneous different logins still require separate browser profiles.

The customer page hides cached content until the account is verified. Confirmed expired sessions detach the private cache; failed session verification stays closed and cannot start autosave. Missing cache-runtime loading also keeps the page closed with a refresh message. Local recovery copies consume browser storage; a quota failure blocks switching instead of deleting unsynced work. These copies isolate application display and writes, and do not provide encryption against someone with access to the browser's developer tools.

Validation includes empty-second-account leakage, unsynced recovery on return, callback detachment, same-account preservation, quota and logout failures, expired/unavailable sessions, provider switching, stale tabs, late responses, native browser Storage and two businesses saving/reloading profiles and buyers through the real persistence boundary. Backend automation and integration credentials are unchanged. Customer OAuth identities are simulated in these regressions; they do not establish acceptance in the customer's signed-in sessions.
