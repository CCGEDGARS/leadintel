## Further connected sending boundaries

- **DP9, high — original source approval:** manual requests now pass the original `source_authority` through the shared server contract before reservation. Profile, Strategy, factual-source and sender edits cannot be sealed to a new current approval by reopening the old request. The original complete workspace row remains asserted inside reservation/dispatch/CRM commits. Missing/forged/stale stamps are tested on both actual routes with zero reservations and zero provider calls. The shared source module and its separate four tests are owned by the parent audit.
- **DP10, high — new-key/provider/path replay:** per-key checks alone allowed an unresolved attempt to be resubmitted under a fresh key or another provider. Manual reservation now atomically excludes other Gmail/Microsoft `sending` rows, another active queue claim and an active supervised mailbox lease. An active pending outreach sequence or supervised plan with future queued/sending steps to the exact recipient also requires explicit cancellation/takeover before manual delivery; its body/status/history are retained. Identical-key races may recover only the hash-matched original receipt, including when a competing accepted send changed CRM before the losing request's context check. Different keys serialize reservations. Queue and supervised acquisition use reciprocal predicates. The hold is deliberately broader than recipient-level uncertainty when an unresolved mailbox reservation exists. It does not prevent a human from independently sending outside these application paths or establish provider-global exactly-once behavior.
- **DP11, high — public profile aliases:** independent real-route reproductions showed a changed `public_linkedin_url` could coexist with the old/empty canonical URL and dispatch through both manual providers, the queue and supervised plans. The shared reviewed-recipient contract now compares the reviewed public fallback and rejects conflicting canonical/public aliases. Queued bindings and supervised original identity/context receipts include the public alias. Changed or unbound historical bindings remain review-required. Existing text and historical evidence are retained.
- **DP12, medium — literal transport:** both provider transports trimmed an explicitly reviewed subject; shared content validation trimmed canonical/rendered/HTML boundaries. Gmail also silently truncated an oversized subject, while Microsoft reserved first and only then rejected it. The four actual-route reproductions in `work/delivery-provider-literal-red.txt` all failed. `validateEmailContent` now preserves exact supplied strings and uses trimming only to test blankness and validate the HTML envelope; raw UTF-8 limits and the security allowlist remain intact. Shared subject validation preserves the literal, rejects invalid controls and rejects over 500 characters before reservation. Gmail MIME and Graph tests now preserve exact subject, body, HTML and linked URL spacing; all four pass in `work/delivery-provider-literal-green.txt`. MIME's required CRLF framing remains a transport representation. No protected master text was changed.

Pre-dispatch and definite provider-rejection responses expose `submission_not_attempted` or `delivery_rejected` when known, rather than forcing the client to infer transport state from a generic error. Uncertain outcomes keep `DELIVERY_UNCONFIRMED` and remain held.

## Frozen continuation and final handoff

The final accepted-revision guard persists a provider-neutral `content_hash` in existing reservation metadata, derived from exact subject, rendered text/HTML, normalized recipient/domain and the original canonical source authority. A fresh key, provider switch or hidden canonical-body-only change cannot resubmit that accepted rendered revision. The original same-provider/key receipt remains readable; a distinct explicitly reviewed rendered follow-up remains possible. Manual, queued and supervised reservations now populate compatible receipts under their own original source guards. No arbitrary new timestamp is accepted as proof of a new review, and no old receipt is silently resealed. Older opaque receipts without a comparable content hash cannot establish cross-provider content equivalence; their original request-bound recovery and uncertainty holds remain. This is an application guard across the audited paths, not universal delivery exactly-once.

Safe control separation is retained: explicit Cancel/takeover releases only known future intent. Neither cancellation, a new review nor a provider switch clears an unresolved transport receipt.
