## Monitoring and operational semantics

Existing Worker configuration has hourly and minute cron entries. Market monitoring is dispatched by the hourly path; minute jobs have a separate purpose. A configured cron is not proof that a customer scheduled execution occurred.

Monitoring processes at most ten due workspaces per hourly invocation. Daily/weekly schedules are elapsed UTC cadence; monthly schedules clamp to the last valid day rather than overflow into the following month. No local civil-time/DST scheduling preference is claimed for this monitor. Missed intervals coalesce into one due run, without a paid catch-up burst. Failures retry at saved cadence; explicit manual run is separate. Existing automatic outreach workflows retain their separately configured timezone/window and delivery authorizations.

New safety controls: 30-second query settlement, five-minute monitor run budget and ten-minute task lease. These are implementation bounds, not measured production latency baselines. Expired leases permit recovery and old owners cannot commit. Duplicate concurrent dispatch references the active run rather than inventing a second completed run. Existing ledger status constraints represent cancellation/stale/skips as failed with safe reason codes; storage failure can itself prevent durable recording.

Operational invariants: zero accepted stale-revision writes, zero duplicate consequential dispatches per active lease, zero paid/send permission inferred solely from Strategy approval. Existing requirements define the hourly ten-workspace limit and saved cadence. Alert thresholds for sustained failure rate, overdue schedules or provider latency require production baselines; any suggested numeric alert thresholds remain proposals, not installed monitoring or observed service levels.
