## Existing stack and actual execution

`backend/wrangler.toml` points to `backend/src/app.js`. The Worker declares minute (`* * * * *`) and hourly (`0 * * * *`) triggers. The scheduled function submits actual work through `ctx.waitUntil`; it does not run in a browser. Cron configuration alone does not establish that a trigger fired or a handler finished.

Minute work comprises writing references, workspace skills, company materials, and language packs. Hourly work comprises market monitoring, source health, saved flows, approved workflows, conversation polling/enrollment/plans, and outreach reply polling followed by outreach delivery. Storage reconciliation runs on existing invocations when its existing feature flag is enabled. No additional schedule, paid probe, notification channel, or monitoring platform is introduced.

`observeScheduledTask` in `backend/src/operational-observability.js` appends `operations.scheduler` start and finish receipts to existing `audit_events`. A generated invocation ID correlates the pair. Metadata contains only schema version, outcome, scheduled time, and measured handler duration. It never contains a provider response, workspace/customer identity, count across customers, raw error, URL, credential, or message. Receipt failure emits a fixed content-free warning and does not prevent business work or replace its result/error.

Every scheduled job is wrapped at the actual entry. A rejected job records `failed`; returned `failed`/`Failed`, partial/no-access results, or failure/hold counters also prevent a false completed summary where those fields are returned. A handler can still swallow an error without returning an outcome: a completed receipt means the handler returned, not that every internal action succeeded. Company-material processing is one such remaining internal-summary gap. Workspace/source/queue records remain necessary evidence. Independent monitoring stays independent of the outreach chain; reply polling must finish successfully before automatic outreach begins.

`operations.stage` is an internal safe hook using the same audit table. Allowed stages are 1 Setup, 2 Profile, 3 Strategy, 4 Companies, 5 Buyers, 6 Messages, 7 Delivery. Allowed outcomes include started/completed/partial/failed/blocked/timed_out/canceled/stale/resumed/retry/duplicate_hold/unknown. Only allowlisted nonnegative integer counters, measured duration, internal action, positive integer revision and canonical opaque UUID operation/run/context correlation IDs are stored. Invalid content-bearing IDs are discarded; an invalid/missing operation ID receives a fresh UUID. There is no client telemetry write endpoint. Both the actual approved-workflow and saved-flow loops wrap execute, current-authority guard and persisted checkpoint. A stage start and terminal receipt share one operation ID and run/revision/action attribution. Profile/Strategy automatic stages validate existing approvals; their `reviewed:1` is not research yield. A helper existing in source does not establish that each manual journey phase calls it: inspect actual call sites and `stageCoverage`; absent observations stay unknown. Browser traces remain separate evidence.

## Safe inspection

Use `GET /api/operations/diagnostics?workspace_id=<active workspace ID>` through the existing authenticated API transport. An explicit workspace is required. The route checks a valid session and membership before reading, then rechecks session, user, and role before returning. Its response is `Cache-Control: no-store`; it exposes no customer text, names, emails, domains, provider/request keys, raw errors, or content-bearing entity IDs. Canonical opaque UUIDs provide safe operation/run/context correlation with a numeric revision. Reads do not prune records, dispatch providers, reconcile accounts, alter settings, or send messages.

The API combines these existing records:

| Projection | Evidence and interpretation |
| --- | --- |
| `release` | Backend configured exact SHA versus the caller-supplied fetched frontend manifest SHA. Missing/invalid revisions remain unknown; a mismatch is critical. This comparison is diagnostic, not an exact-SHA release-proof substitute. |
| `scheduler` | Actual safe handler receipts; no history is `unknown`, unavailable storage is `unavailable`. Global task names/status/times expose no other tenant data. |
| `stageCoverage`, `stageReceipts` | Wired durable stage outcomes, duration and safe counters. They are observations in a bounded sample, never proof the whole stage/business goal completed. |
| `queue` | Automation states, attempts, age, overdue time, duplicate/ambiguous holds. A `sending` state remains uncertain. |
| `workflow` | Persisted run state, stage index, approved/current revision, mismatch and lease expiry. No private result snapshots are returned. |
| `monitoring`, `monitoringConfiguration`, `sourceHealth` | Actual saved query/source/alert counts, duration, configuration revision, schedule and lease, saved source access/failure states. Planned/configured sources are not executed coverage. |
| `research` | Legacy dispatch/run state, candidate budget versus retained use, attempts, measured completion duration and missed stored deadline. Accepted dispatch does not establish completed research. |
| `delivery.gmail`, `delivery.microsoft` | Stored provider submission states. Fresh sending is `inFlight`; old/explicit unknown submission is uncertain. `sent`/Microsoft accepted means provider acceptance, not recipient delivery or inbox placement. |
| `delivery.acceptanceReceipts` | Existing `email.delivery_accepted` receipts compared with same-workspace message status. Recorded acceptance with missing/unsent state is a persistence mismatch. Receipt bodies and hashes are never projected. |

## Bounds and interpretation

The projection reads at most 201 rows per source to return at most 200 and disclose `moreAvailable`. Recent terminal events cover seven days. Open/uncertain queues, workflow leases, dispatches, contact reservations and unsynced outbox records remain eligible beyond seven days and are sampled first. This prevents a newly opened diagnostics view from hiding an old stuck send just because its creation date is outside the window. If more than 200 open rows exist, some are omitted: every count is a sample count, never an all-time total or clean bill of health. Source/configuration views are bounded independently.

The new writer prunes only `operations.scheduler` for the same task and global NULL-workspace scope, or `operations.stage`/`journey` for the same workspace. Existing provider acceptance, paid lookup, CRM and customer audit evidence is preserved. Retention is at most 30 days and at most 512 scheduler receipts per task (start plus finish) or 1,000 stage receipts per workspace, whichever limit is reached first. At two minute receipts per invocation, 512 minute-task receipts represent roughly 256 minutes; hourly tasks retain roughly 256 hours. This is an upper bound, not guaranteed complete history. Pruning is atomic with append in the existing D1 batch and occurs on writes; an inactive namespace can retain older rows until its next append. Existing `(workspace_id, created_at)` audit indexing includes NULL workspace rows; no new schema migration is required.

Raw customer text is never copied into new operational records. Treg monetary aggregation uses private call IDs only inside the server and removes them before responding. Positive consistent saved receipt amounts are the known subtotal; zero, absent, invalid, conflicting or missing amounts stay unknown. If receipt rows are truncated, the amount is null. A known subtotal alongside unknown receipts is partial evidence, not total spend; no receipt history is never a zero-charge assertion. Provider settlement, missing receipts, AI/Firecrawl/Apollo/Hunter spend and all-in acquisition cost remain unknown here.

## Detection and severity

There is no measured production latency/error baseline or numeric availability SLO in this audit. Thresholds below distinguish existing runtime limits from proposed investigation grace; none automatically retries, sends, pays, activates or notifies.

| Condition | Severity / action | Basis |
| --- | --- | --- |
| Valid frontend/backend SHA mismatch | Critical: pause affected automatic actions, inspect intended source and exact release proof, then verify both artifacts before resuming. | Explicit equality rule for two known revisions; no latency threshold. |
| Latest actual scheduled handler failed | Critical: investigate the failed handler and workspace-specific outcomes. | Observed rejected invocation or explicit failed returned outcome. A later successful handler receipt resolves that latest-handler condition, not every business issue. |
| Missing scheduler receipt history / storage unavailable | Unknown: establish authenticated actual execution and storage availability. | No invented heartbeat or missed-run count from cron configuration. |
| Latest start/receipt older than twice its task cadence | Important: investigate possible missed trigger, hung work, receipt failure or blocked chain. | **Proposal:** 120 seconds for minute tasks, 7,200 seconds for hourly tasks. Not a measured SLA or proof a particular number of runs was missed. |
| Explicit unknown provider submission/allowlisted unconfirmed event, or sending/unconfirmed outbox beyond its grace | Critical: hold duplicate dispatch and reconcile. Fresh `sending` is in flight rather than a confirmed failure. | Explicit unknown outcomes need no delay. **Proposal:** five-minute general submission/persistence grace; supervised follow-ups already use a five-minute interrupted-attempt rule. Neither threshold proves the provider failed. |
| Acceptance receipt versus unsent/missing message state after grace, or recorded post-send sync failure | Critical: recover persistence/CRM without another send. Fresh acceptance before its status write is `sync_pending`. | Recorded discrepancy after the **proposed** five-minute persistence grace, or immediate safe allowlisted sync failure. |
| Stored run lease expired / run revision differs from current revision | Important: inspect the current owner/revision and retained receipts before resume. | Existing stored lease/deadline/revision. Missing lease on a running run is treated as expired, never current authority. |
| Legacy research stored deadline passed | Important: review dispatch receipt and retained partial results. | Existing per-run deadline (created with the existing 20-minute run deadline). |
| Delivery queue/follow-up or unleased enabled monitoring overdue by two hours | Important: inspect scheduling window, policy, suppression, approvals and heartbeat. | **Proposal:** 7,200-second grace aligned with two hourly scheduler cycles, not a promised send time. |
| Source health `failing` | Important: inspect actual extraction receipts and access gaps. | Existing source-health policy: at least three consecutive unsuccessful access audits. This is not a new paid probe. |
| Retained provider reservation/processing/needs-review state | Important: reconcile provider-started and settlement receipts before spending again. | Existing durable reservations; a client cancel or permission change does not prove a submitted charge disappeared. |
| Pending ready CRM outbox | Important: inspect CRM persistence and replay its existing recovery path. | Existing durable unsynced outbox. No fresh provider submission is required. |
| Any unavailable projection or `moreAvailable` | Unknown/incomplete: inspect the underlying authorized source; avoid absence-based conclusions. | Bounded sample and explicit source failure. |

Start investigation with the precise finding, generated time, active workspace, sample truncation and failed task/stage. Compare the existing exact release proof, current approved revision, stored state and provider acceptance/credit receipts. Do not infer customer success from a green health endpoint, configured connection, zero sampled errors or completed scheduler handler.

## Pause, reconcile and recover safely

1. Preserve the failed/uncertain receipt and active revision. Pause through the existing owner controls in Delivery/My Flows/Strategy monitoring as appropriate. The existing automation policy has pause/emergency-stop controls; saved flows and approved workflows have pause/manual/stop actions. Use dedicated operational controls rather than Ask LeadIntel, which is advisory only. Pausing prevents future authorization; it cannot recall an already accepted provider submission.
2. For deliberate manual takeover of a known pending legacy outreach sequence, use its dedicated **Cancel future steps** action in the Delivery queue and confirm the exact recipient. The server checks the original sequence/steps and current owner session atomically. Pause alone retains future intent. Cancellation preserves prior sent history and cannot release a sending/unknown reservation or recall an accepted message. Supervised plans use their existing guarded cancel/takeover controls.
3. For an uncertain send, retain the original idempotency key, exact approved message/recipient snapshot, provider, mailbox identity and request binding inside authorized records. Inspect whether provider acceptance was durably recorded and whether the message, queue, CRM/outbox and browser acknowledgement agree. Use existing receipt-based status recovery. A changed/new idempotency key is a new dispatch and must not be used to bypass an uncertain hold. No recovery instruction here authorizes a send.
4. For accepted-but-unsynced work, use existing status/acceptance/outbox recovery and reload. Restore CRM state from retained acceptance/evidence, not by repeating the provider call. If acceptance itself was not durably recorded, the outcome stays uncertain until authorized provider/mailbox reconciliation establishes it. Never replace unknown with failed/zero solely to unblock a retry.
5. For provider charges or paid lookup reservations, compare actual saved provider-started and call/credit receipts with the provider's separately authorized settlement evidence. Keep submitted/unknown reservations retained. Only a proven pre-dispatch failure may release its existing pre-dispatch hold. Stopping, deleting, revoking permission, timing out or cancelling does not reverse a charge that may already have been submitted.
6. For expired workflows/leases or changed revisions, reload the current workspace/flow, review retained checkpoints and approval requirements, then use the existing owner retry/resume controls only after uncertainty is reconciled. Do not clear leases, erase runs or edit SQL statuses manually to make a dashboard green. Resume/retry may execute paid research or dispatch; the operator must use the current explicit authorization and the dedicated confirmation flow.
7. For research shortfall, inspect Known → Planned → Researched → Verified evidence, actual tool receipts, mandatory-source failures, buyer coverage/review and currently usable confirmed company emails. Provider rows, query counts, model review, contact count and message readiness are separate outcomes. Preserve incomplete research and partial usable results; never pad output or rerun paid work just to satisfy an operational percentage.
8. After recovery, read diagnostics again and verify save/reload, downstream CRM and the intended business outcome separately. A cleared latest-handler error or restored persistence is not evidence a recipient received a message, a provider refunded a charge, or buyer acceptance is complete.

Useful existing read routes include `/api/flows`, `/api/approved-workflow`, `/api/outreach-automation/status`, `/api/market-monitoring/runs`, `/api/market-monitoring/config`, `/api/intelligence-sources`, `/api/research/costs`, and `/api/operations/diagnostics`; they require their current workspace/session permissions. Follow-up conversation details remain under their existing authenticated routes. Read routes may contain private evidence outside this safe diagnostic API; do not publish their raw output.
